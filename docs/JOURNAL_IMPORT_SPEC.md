# Legacy Journal Importer 规格

> 状态：Phase 3 本地修正与 Dry Run staging 切片已实现
> 版本：0.3
> 最后更新：2026-08-31
> 范围：巨大 Word 文档中的多年纯文字日记，解析为可预览、可审计的 Journal/Markdown 数据。

当前实现边界：PWA 可在浏览器内选择 `.docx` 工作副本，计算源 SHA-256，只解压 `word/document.xml`，提取段落、样式/大纲/加粗/字号提示，按源顺序识别中文或阿拉伯数字年/月/日/时间，并展示按日 Markdown、继承上下文、置信度、orphan、不支持对象和 diagnostics。用户可以为异常或低置信度段落追加带原因、时间和 `supersedesId` 的本地修正，立即重解析并查看差异；结构通过后可下载包含 staging Markdown、machine-readable manifest 和不复制正文的 Import Log 的确定性 ZIP。文件不上传、不修改，不写 GitHub、Journal 或 Vault；Commit 能力固定关闭。当前没有 Import Log 持久化、正式批量提交或 Obsidian 写入。

## 1. 目标

在不修改原始 Word 文件、不静默丢弃内容的前提下，识别年、月、日、时间与正文，经过用户预览确认后生成 Personal Workspace 日记和 Obsidian 可读 Markdown，并输出完整 Import Log。

成功不等于“解析器没有报错”，而是：每一段源内容都有明确去向，日期异常可见，结果可抽查，重复执行安全，出现问题可回滚。

## 2. 非目标

- Phase 0 不实现解析器或处理真实日记。
- 不原地修改、重排或另存覆盖原 Word。
- 不在没有预览和确认的情况下直接写入正式 Journal/Vault。
- 不对正文做 AI 改写、润色、总结或情绪推断。
- 不推测无法确定的年份/日期后静默入库。
- 不承诺保留 Word 中所有视觉排版；目标是结构和纯文本内容的可靠迁移。
- 当前样本无图片；若发现图片、表格、批注、脚注、文本框或嵌入对象，进入异常报告而不是忽略。

## 3. 输入与前置条件

### 3.1 支持范围

首选输入：`.docx`。如果原件是旧 `.doc`：

1. 保留原始 `.doc` 不动。
2. 使用可信工具创建一个 `.docx` 工作副本。
3. 同时保存两者哈希和转换工具/版本。
4. 在 preview 中标记“经过格式转换”。

### 3.2 导入前准备

- 对原件做只读备份，建议至少两个独立位置。
- 记录文件名、字节数、修改时间和 SHA-256。
- 从原件复制工作副本，所有解析只针对副本。
- 确认默认时区、默认语言和日期书写习惯。
- 提供脱敏的小样本文档，用于建立解析规则和测试集。
- 导入正式数据前备份当前数据库与 Obsidian Vault。

## 4. 用户流程

```text
选择 Word 副本
  → 文件检查与指纹
  → 只读解析
  → 结构识别
  → Preview + Diagnostics
  → 用户修正规则/单条记录
  → Dry Run 生成 Markdown
  → 用户确认 Commit
  → Journal + Vault 输出
  → Verification + Import Log
```

任一步都不得覆盖源文件。Commit 之前的结果全部位于 staging。

## 5. 解析管线

### 5.1 文档提取

按原始顺序提取：

- 段落文本。
- 段落样式名和大纲级别。
- 加粗、字号等有限格式提示，仅用于提高标题识别置信度。
- 空段落数量，用于保留合理的正文分隔。
- 表格单元格、文本框、脚注等特殊容器的存在和内容定位。
- 页码/段落序号等 source locator，便于回查。

不得仅按视觉换行切分，因为 Word 的软换行、段落和分页符语义不同。

### 5.2 文本规范化

规范化只用于匹配，原始文本副本始终保留：

- Unicode 规范化。
- 全角/半角数字和冒号的匹配兼容。
- 去除匹配用的首尾空白。
- 将连续空白用于标题匹配时折叠，但正文输出保留段落结构。
- 兼容中文数字和阿拉伯数字的年/月/日。

不得自动纠正正文错别字、标点或表达。

### 5.3 结构 token

解析器将段落分类为候选 token：

- `YEAR_HEADING`
- `MONTH_HEADING`
- `DATE_HEADING`
- `TIME_HEADING`
- `BODY`
- `EMPTY`
- `UNSUPPORTED_OBJECT`
- `AMBIGUOUS`

分类依据结合文本模式、Word 样式、上下文顺序和取值合法性，不能只看字号或只用单个正则。

### 5.4 推荐识别样式

以下只是初始规则族，必须用实际样本校准：

#### 年

- `2012`
- `2012年`
- `二〇一二年`
- `二零一二年`

合法范围由用户确认文档年代后配置；明显超出范围标为 error。

#### 月

- `1月`、`01月`、`一月`
- 可能只有 `1` 且使用月份标题样式，此时置信度较低并依赖上下文。

#### 日

- `3日`、`03日`、`3号`
- `3月5日`、`03-05`、`3/5`
- 完整日期 `2012-03-05` 或 `2012年3月5日`
- 星期文字可作为校验信号，但不应单独决定日期。

#### 时间

- `02:23`、`2:23`、`02：23`
- 可扩展识别 `上午 8:30`、`23:10`。
- 24 小时制的小时为 0–23、分钟为 0–59。
- `24:00` 进入异常，不自动变成次日 00:00。

### 5.5 状态机

解析状态包含当前 `year`、`month`、`day`、`time`：

1. 年标题更新 year，并清空 month/day/time。
2. 月标题要求已有 year，更新 month，并清空 day/time。
3. 日标题结合显式值和当前上下文构造日期，清空 time。
4. 时间标题要求已有可确定日期，开启一个 JournalSegment。
5. BODY 追加到当前 segment；如果只有日期没有时间，追加到无时间 segment。
6. 新的同级标题关闭上一 segment/entry。
7. 无有效日期的正文进入 orphan block，绝不丢弃。

状态机必须记录每次上下文继承，让 preview 能说明某条记录的年份/月来自哪里。

### 5.6 日期合法性与顺序

- 使用真实日历验证闰年、月份天数和完整日期。
- 日期回退不必然是错误，可能是原文排序；标为 warning 并展示相邻记录。
- 重复日期允许存在；同日多个时间片段应合并到同日 Journal 或按用户策略保留。
- 同日时间倒序标为 warning，不自动排序；可在输出时按源顺序或时间排序，由用户选择，默认保留源顺序。
- 缺失年份/月/日时只有在上下文唯一明确时继承，并记录置信度。
- 不存在的日期、无上下文日期、跨年边界异常为 blocking error。

## 6. 置信度与诊断

### 6.1 置信度

每个结构判断保存 `high / medium / low` 或等价数值，并列出依据：

- 文本完全匹配。
- 使用 Word 标题样式。
- 上下文顺序合理。
- 日期合法。
- 与相邻标题一致。

置信度只用于排序复核优先级，不能替代用户确认。

### 6.2 诊断等级

- **Info**：正常继承上下文、格式被规范化等。
- **Warning**：顺序回退、重复日期、可疑标题、正文内疑似时间。
- **Error**：非法日期、孤立正文、无法解析的必需上下文。
- **Blocking**：源文件损坏、加密、解析中断、输出路径冲突或完整性检查失败。

### 6.3 不得静默忽略

以下内容必须出现在 preview/log：

- 无日期归属的正文。
- 无正文的日期或时间标题。
- 不支持的对象或容器。
- 空白但具有标题样式的段落。
- 疑似日期/时间但非法的文本。
- 被跳过、被用户改写或被合并的条目。

## 7. Preview 规格

### 7.1 批次摘要

- 源文件信息与哈希。
- 解析器、规则和映射版本。
- 识别的年份范围、日期数、segment 数、正文字符数。
- Info/Warning/Error/Blocking 计数。
- 重复候选、孤立块、不支持对象计数。

### 7.2 条目预览

每条展示：

- 解析出的日期、时间和时区。
- Markdown 预览。
- 对应源定位和原始片段。
- 继承的上下文与置信度。
- 诊断、重复候选和计划输出路径。
- 状态：pending、edited、skipped、approved、blocked。

### 7.3 用户可执行动作

当前实现的安全子集是：将单段解释为完整日期标题、时间标题或正文，把孤立正文指派到明确日期/可选时间，或填写原因后跳过；每次修正都会追加审计记录并比较重新解析结果。下面其余动作仍是后续能力：

- 修改日期/时间。
- 将段落重新标记为年/月/日/时间/正文。
- 合并或拆分条目。
- 把 orphan block 归入某日。
- 选择跳过并填写原因。
- 批量应用明确规则，然后重新解析并比较差异。
- 筛选“仅异常”“低置信度”“重复候选”“已修改”。

任何手工修正都保存原值、新值、时间和原因，重新解析不能静默抹掉修正。

## 8. 去重与幂等

### 8.1 批次幂等

`source SHA-256 + parser version + mapping version` 标识解析批次。再次选择相同原件时提示已有批次，可继续、复制为新规则试验或查看已提交结果。

### 8.2 条目去重键

候选键可由以下组合生成：

- 源文件 SHA-256。
- source locator。
- 规范日期/时间。
- 规范正文哈希。

还需对现有 Journal 做相似候选检查：相同日期/时间和正文哈希为强重复；相同日期与高文本相似度为弱重复，仅提示不自动删除。

### 8.3 重试

Commit 为幂等操作。每个 staging entry 记录目标 Journal ID 和输出哈希；重试只处理未成功项或校验失败项，不重复创建成功项。

## 9. Markdown 输出契约

### 9.1 默认路径

建议一天一文件：

```text
Journal/YYYY/YYYY-MM-DD.md
```

若同日已有用户日记，不直接覆盖；进入 merge preview 或 conflict。

### 9.2 Frontmatter 示例

```yaml
---
type: journal
date: 2012-03-05
timezone: Asia/Shanghai
source: legacy-word-import
import_batch_id: "<stable-id>"
schema_version: 1
---
```

公开文件不应包含本机绝对路径。内部批次 ID 可选；如用户希望 Vault 更纯净，可将详细溯源只放在数据库和 manifest。

### 9.3 正文示例

```markdown
## 02:23

内容……

## 04:24

内容……
```

无时间正文放在时间段之前或 `## 未记录时间` 下，具体模板在 dry run 中确认。正文中原有类似 Markdown 的字符应保证渲染安全且尽量忠实，不进行语义改写。

### 9.4 文件写入

- 先写临时文件，校验后原子重命名。
- 目标存在时对比哈希；不无条件覆盖。
- 文件编码 UTF-8，换行策略固定并记录。
- 生成后重新读取并计算 SHA-256。

## 10. Commit 与事务

建议分两步：

1. **Dry Run**：在隔离输出目录生成全部 Markdown、manifest 和 log，不触碰正式 Journal/Vault。
2. **Commit**：用户批准指定条目后，创建数据库记录，再通过受控同步 Job 写入 Vault。

批量提交使用小批次检查点，避免巨大事务。每个小批次要么完整成功，要么回滚；整批可部分完成，但 UI 必须准确显示已提交与未提交范围。

## 11. Import Log 与 Manifest

### 11.1 Import Log

人类可读日志至少包含：

- 批次 ID、开始/结束时间、操作者。
- 源文件元数据与 SHA-256。
- 解析器、规则、映射和输出 schema 版本。
- 总计数、成功、跳过、warning、error、冲突。
- 每条异常的 source locator、原因、用户决定。
- 手工修正摘要。
- 数据库目标 ID 和相对 Markdown 路径。
- 回滚/重试记录。

日志不需要复制每篇完整正文；通过哈希和受控引用关联，避免产生又一份敏感全集。

### 11.2 Machine-readable Manifest

建议 JSON/CSV 包含：

- source locator。
- parsed datetime 与时区。
- content SHA-256。
- staging ID、Journal ID。
- relative output path、output SHA-256。
- status、diagnostic codes、manual edit flag。

## 12. 验证与对账

### 12.1 自动验证

- 源段落覆盖率：所有非空内容属于 entry、unsupported 或 orphan。
- 输入与 staging 的字符/段落对账，允许的规范化差异明确列出。
- 日期合法性和范围。
- Journal 数、segment 数、Markdown 文件数和 manifest 数量一致。
- 所有输出文件哈希可复算。
- 所有数据库目标引用存在。
- 重新运行相同 commit 不新增重复记录。

### 12.2 人工抽样

建议至少覆盖：

- 每个年份的开头、中间、结尾。
- 跨月、跨年、闰日和日期回退。
- 同日多时间段。
- 无时间正文、超长正文、空记录。
- 每种 warning/error 修正类型。
- Word 样式变化明显的不同年代。

正式导入应按年份或可控批次进行；每批批准后再继续下一批。

## 13. 回滚

- Commit 前可直接丢弃 staging，不影响正式数据。
- Commit 后按 `import_batch_id` 生成回滚预览，列出将删除/解除关联的 Journal 和文件。
- 只自动回滚自导入后未被用户编辑、未被其他对象引用的内容。
- 已编辑或发生同步冲突的条目进入人工处理，不强制覆盖。
- 文件移入可恢复隔离区，数据库使用软删除；保留期过后才允许永久清理。

## 14. 本地 Preview、修正与 Dry Run 切片验收

- `.docx` ZIP 与 `word/document.xml` 全部在当前浏览器内处理；不调用上传或服务器解析接口。
- 限制源文件 256 MiB、主文档 XML 64 MiB、ZIP 条目 20,000，并拒绝路径穿越、加密包、损坏 ZIP 和缺失主文档。
- 图片、表格、批注、脚注/尾注、页眉/页脚、嵌入对象、文本框、字段和宏必须产生明确 diagnostic；宏为 blocking。
- 非法日期/时间会清空当前归属状态，后续正文进入 orphan，禁止误挂到上一日。
- 脱敏 OOXML/ZIP fixture 覆盖中文年份、上下文继承、全角时间、同日多 Segment、无时间正文、日期回退、非法 24:00、表格和媒体报告。
- UI 只渲染最多前 100 条按日预览以避免巨大文档阻塞；汇总和 diagnostics 仍覆盖全文。
- 手工修正按 source locator 校验，理由必填；同段后续修正必须精确取代上一条，不支持对象只能明确跳过。
- 每次修正使用同一源文件和完整修正链重解析，并展示新增、删除、变化日期及 diagnostics/orphan 计数差异。
- Dry Run 只在没有 error/blocking、所有非空段落均有明确去向时开放；ZIP 包含 `staging/Journal/...`、`manifest.json` 和 `import-log.md`，所有输出有 SHA-256，目标 Journal ID 为空、状态为 pending、`commit_enabled = false`。
- ZIP 条目顺序、mtime、输出路径和默认审计时间锚点固定；对同一 preview 重复生成得到相同 ZIP。显式传入时间时，该时间视为确定性输入。
- Import Log 记录源指纹、修正链、跳过原因、diagnostics 与输出哈希，不复制日记正文。
- 下一切片才允许设计幂等正式 Commit；仍需独立事务、冲突、恢复与逐批确认。
- 回滚本身生成 AuditEvent 和 Import Log 追加记录。

## 15. 性能与资源安全

- 流式/分段解析巨大文档，避免全部对象常驻内存。
- 限制文件大小、解压后大小、段落数、单段长度、处理时间和并发数。
- Job 定期写检查点和心跳，失败后可从安全边界重试。
- 解析器在隔离环境运行，不执行宏、链接或嵌入对象。
- Preview 分页和虚拟化，不能一次渲染十多年全文。

## 16. 隐私

- 原 Word、staging 正文、dry-run 输出和日志都属于 Restricted。
- 默认不将正文发送给 AI 或第三方转换服务。
- 若必须使用外部格式转换，需单独明确授权；首选本地可信工具。
- 临时文件在 Job 完成/失败后按策略清理，路径和内容不进入普通日志。
- 导入完成后用户选择保留或删除服务端工作副本；原件备份策略单独说明。

## 17. 测试矩阵

- 阿拉伯/中文数字年月日。
- 全角冒号、不同空格、不同换行。
- 闰年、非法日期、`24:00`、日期倒序。
- 只有日期无时间、只有时间无日期、连续多个时间。
- 标题文字与正文中的日期/时间相似文本。
- 同日多条、重复正文、已存在目标文件。
- 损坏、加密、旧 `.doc` 转换、超大文件。
- 表格、图片、脚注、文本框等意外对象。
- 中途失败、重试、取消、回滚和同步冲突。

## 18. 验收标准

- 原文件字节和 SHA-256 在导入前后不变。
- Commit 前存在完整 preview，blocking error 必须解决或明确排除。
- 非空源内容覆盖率为 100%，无静默丢弃。
- 同批次重复提交不会创建重复数据。
- 输出日期、时间、正文和路径通过自动对账与人工抽样。
- Import Log 和 machine-readable manifest 可定位每条输出来源。
- 模拟冲突和回滚不会覆盖导入后的人工作品。

## 19. 需要用户提供/确认

进入 Phase 1/3 技术验证前需要：

1. 原文件格式是 `.docx` 还是 `.doc`，大致文件大小和年份范围。
2. 一份不含敏感内容但保留真实样式的样本文档。
3. 年/月/日标题的实际写法及是否使用 Word 标题样式。
4. 日记默认时区，历史期间是否长期为 `Asia/Shanghai`。
5. 同日内容输出为一个 Markdown 文件还是多个文件；建议一天一文件、多时间段二级标题。
6. 无时间正文、重复日期和已有同名文件的首选处理规则。
7. 导入原件、工作副本和日志的保留期限。
